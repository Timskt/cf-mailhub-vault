# 备份、恢复与迁移边界

本文依据当前 `src/routes/backups.ts`、`src/storage/coordinator.ts`、凭据加密和邮件对象回收实现编写，核对日期为 2026-11-16。

当前提供的是**有大小限制的业务便携备份与恢复**。完整灾备还需要数据库原生备份、独立的 R2 文件、加密密钥、Worker 配置以及 Durable Object 协调器控制态。项目目前没有完整控制态的导出/导入接口，不能据此承诺一键跨 Cloudflare 账号恢复整个站点。

## 选择备份方式

| 方式               | 保存范围                                                         | 恢复前提与限制                                                                 |
| ------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 脱敏业务清单       | 白名单中的业务元数据，不含账号密码、令牌、正文等敏感内容         | 用于核对和统计；`restorable: false`，不能恢复                                  |
| 加密业务便携备份   | 下述 12 张业务表及少量偏好；包括平台目录、账号凭据、CF 邮件正文与对象引用  | 明文 JSON ≤ 1 MiB，总计 ≤ 1,000 行；目标应用、协调器、密钥和依赖文件须先可用   |
| D1 原生 SQL 导出   | 所选 D1 数据库中实际存在的表、行、数据集元数据和迁移记录         | 不包含外部主库、DO 存储、Worker Secrets 或 R2 文件；恢复后须核对活动数据集指针 |
| 外部数据库原生备份 | MySQL/MongoDB/Redis 中的应用数据、generation 与版本/所有者元数据 | 使用相应数据库的一致性备份与恢复流程；还需要原协调器和密钥配套                 |
| 应用“同步副本”     | 同步任务完成时的一个校验过的数据集                               | 不是持续复制，不包含 R2 文件或完整 DO 控制态；后续写入需重新同步               |

生产安排应同时定义恢复点目标（允许丢失多长时间的数据）、恢复时间目标、保留周期和定期恢复演练。界面显示“同步完成”只能证明这一次数据集同步，不能证明独立灾备已完成。

## 业务便携备份的准确范围

可导出并恢复的表为：

```text
settings, groups, tags, accounts, account_tags, cf_inbox_mails,
mail_rules, platforms, platform_vault, temp_emails, temp_mailboxes, domains
```

`settings` 仅包含 `default_prefix`、`mail_retention_days`、`token_refresh_batch`、`default_mail_domain`。Outlook 备份包含账号与刷新令牌，不会下载或备份 Microsoft 服务器上的邮箱内容；令牌的实际有效性仍取决于 Microsoft。

以下内容不从便携文件导入：管理员/会话认证设置、API Key、OAuth 会话、幂等请求记录、审计日志、Webhook 配置与投递队列、推送进度、对象 GC 队列、数据源连接、DO 协调器状态、Worker Secrets、R2 对象内容、DNS/Email Routing 和微软应用注册。

恢复时，业务表被替换为备份中的内容，**不是逐行合并**；目标当前数据集中的控制记录会复制到新的数据集。保留的推送记录与 OAuth 会话如果引用了备份里不存在或身份不同的账号/分组，恢复会拒绝切换。新 Cloudflare 账号中的新环境不会因此获得旧环境的控制记录。

实现中的格式为 `mailhub-backup` / version `1`，当前 schema version 为 `11`。新增的 `platforms` 保存独立平台目录，包括空平台、名称、官网、分类、备注、置顶和创建/更新时间；恢复时目录与账号一起替换。普通账号的文本、CSV 或 `/api/vault/export` JSON 不包含空平台目录，不能代替完整业务备份。

### schema 10 兼容

支持已发布的 schema `10`（11 表）备份，处理顺序是：

1. 依据冻结的 schema 10 字段/主键投影核对原 `schema_hash`，要求原 11 张表及清单键完整且精确，不接受夹带 `platforms` 或任意新字段。
2. 验证原逐表/整体哈希、类型、主键、唯一约束、允许的偏好及账号/邮箱关联。含凭据的明文即使有效也不能通过 HTTP 恢复；旧脱敏明文仅供预览。
3. 通过后在内存中根据 `platform_vault` 生成平台目录：按账号 ID 排序，平台名去除两端空格并不区分大小写。首条账号提供显示名、安全 HTTP(S) 官网、分类和时间；平台备注为空、置顶为 0。全部账号原字段原样保留，包括各自的官网、分类、备注、置顶和大小写变体；非法历史官网保留在账号原字段上，不提升为平台链接。
4. 重新生成 schema 11 清单、计数和哈希，并重新验证完整文档。预览的 `table_counts`、`backup_hash` 对应转换后内容；恢复仍提交原上传文件。转换不读取当前时间或目标目录，因此重复预览、确认恢复的摘要一致。

旧文件没有独立的空平台记录，无法凭空恢复这些记录。目标原有平台目录不会被混入旧文件的恢复结果。新增派生平台也占用 1,000 行/1 MiB 容量，超过后返回 `BACKUP_TOO_LARGE`，不会静默丢弃平台。未知未来版本、其他旧版本、原始哈希不匹配及手工只改版本号的文件都会拒绝；需要在相应版本的隔离环境另行迁移。

### 容量与加密

- **1 MiB = 1,048,576 字节**，按解密后 `JSON.stringify(document)` 的 UTF-8 字节数计算，包含 manifest；不是可容纳 1 MiB 正文的承诺。导出还为清单预留 12,000 字节，实际可导出行数据会略小于名义上限。
- 1,000 行是全部业务表合计；每个标签关联、域名和偏好也计一行。
- HTTP 请求体上限为 2 MiB，用于容纳 Base64 加密封装、口令和确认参数；这不会扩大明文数据上限。协调器另有 2 MiB 的已加密业务表保护上限。
- 完整业务导出要求显式确认并设置至少 12 字符的备份口令。文件采用 AES-256-GCM，PBKDF2-SHA256、100,000 次迭代、随机 salt 和 IV；口令不写入文件。建议用密码管理器生成并独立保管高熵口令。
- 导出读取的是解密后的业务凭据，再用备份口令加密。恢复时使用**目标的当前凭据密钥**重新加密；导入一个已经成功生成的便携文件不需要原环境的凭据密钥，但需要正确的备份口令。
- 原生数据库备份保留原有密文，需要备份时使用的密钥。历史明文记录也可能存在，因此 SQL、数据库快照和便携文件都应按敏感材料保管。

## 小规模业务恢复与 1 MiB 验证

先在独立测试部署演练，使用虚构账号，关闭其邮件接收、定时任务和外部通知。准备与备份兼容的代码和 migrations、可工作的 `DB` 与 `STORAGE` 绑定、至少 32 字符的目标凭据加密密钥。备份引用原始邮件时，先恢复对应 R2 对象。所有备份管理接口要求管理员会话，自动化 API Key 不能代替会话。

操作顺序如下；JSON 中的口令只表示字段位置，真实值应由受保护的客户端输入，避免进入 shell 历史或日志。

| 步骤           | 方法与路径                                         | 请求/核验                                                                                                                                           |
| -------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 查看能力       | `GET /api/backups/manifest`                        | 检查限制、schema、排除范围与 `restore_available`；该标志不等于数据库/R2 健康检查                                                                    |
| 导出清单       | `GET /api/backups/export`                          | 只做脱敏核对，不能用于恢复                                                                                                                          |
| 导出可恢复文件 | `POST /api/backups/export`                         | `{ "include_credentials": true, "confirm": "EXPORT_CREDENTIALS", "passphrase": "<独立备份口令>" }`；响应本身就是加密文件                            |
| 预览           | `POST /api/backups/preview`，或同义路径 `/dry-run` | `{ "backup": <加密文件对象>, "passphrase": "<口令>" }`；检查行数、哈希、依赖与 `confirmation_token`                                                 |
| 恢复           | `POST /api/backups/restore`                        | `{ "backup": <同一对象>, "passphrase": "<同一口令>", "confirmation_token": "<预览返回值>", "confirm": "RESTORE_BACKUP" }`；必须带 `Idempotency-Key` |
| 核验           | 业务列表/详情与 `GET /api/settings/storage`        | 比较行数、账号关联、正文和附件，确认新的 `active.generation` 及 `previous`                                                                          |

预览 token 绑定当前管理员会话、备份内容、当前业务摘要和活动数据集，10 分钟后过期。`restorable: true` 仅描述文件；没有 token 时不能执行恢复。`writes_performed: false` 表示预览不应用备份业务数据；请求仍可能产生审计或安全控制记录。

执行恢复前会再次核对业务状态、数据集版本和 R2 文件存在性。协调器在独占队列内检查对象的 `deleting` 标记、保留控制记录的关联，写入同一 Worker 所绑定 D1 的新 `restore-…` generation，逐页回读比较摘要、数量、版本与 ID 计数器，最后原子保存活动指针和恢复回执。原数据集保留。即使原活动库是 MySQL/MongoDB/Redis，本次便携恢复的目标仍是 D1；后续移回外部库要另做同步切换。

收到 `BACKUP_CHANGED`、`BACKUP_PREVIEW_EXPIRED` 时重新预览；收到 `BACKUP_BUSY` 时先完成或取消迁移、处理待提交写入。网络超时后应使用相同会话、完全相同请求和相同 `Idempotency-Key` 核对/重试；`IDEMPOTENCY_UNKNOWN` 表示需要核对状态，不能自动换 Key 重做。不要将保留旧 generation 理解为已提供一键灾备回滚。

**目标当前业务数据也需要通过 snapshot 的容量和解密检查。** 不能用一个小便携文件直接覆盖已经超过导出限制、主库离线或旧凭据无法解密的目标。保留控制记录还受 10,000 行/16 MiB 的上限约束。这类情形应采用数据库原生恢复或先制定数据集迁移方案。

### 发布前生产原生恢复证据

发布任务应使用**发布前最新的生产原生备份**，在隔离资源中完成恢复演练，将实际结果补入对应发布记录。本文的本地 1 MiB 演练和自动化测试不替代这份证据；在取得证据前，不标记生产灾备或跨账号恢复已通过。

| 证据项           | 发布记录应包含的实际内容                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 备份来源与时间   | 源账号/资源标识、实际主库类型、活动 generation/revision、UTC 备份时间、代码及 migrations 版本；说明与发布之间的写入窗口 |
| 原生备份产物     | 受控保存位置、文件字节数、SHA-256、导出命令与退出状态；备份正文、密钥和连接凭据不进入仓库或公开日志                     |
| 隔离恢复         | 目标资源标识、导入和迁移执行结果、开始/完成时间；明确目标与生产隔离，外部通知和邮件发送未被演练触发                     |
| 数据与文件核验   | 表/行数、版本与计数器、关联一致性、凭据解密结果；R2 独立副本及对象摘要，原始邮件和附件抽查结果                          |
| 协调器与密钥覆盖 | 本次是否实际恢复 DO 控制态、是否保留原协调器、使用哪些密钥版本；未覆盖的部分明确列为未验证                              |
| 恢复结论         | 实际耗时、可恢复到的时间点、未覆盖资源与故障场景、验证记录链接及负责人                                                  |

如果本轮只验证 D1 SQL 导入，应将结论写为“该 D1 备份在隔离目标恢复并核验通过”；不能由此推断外部主库、DO、R2、密钥恢复或跨账号全站接管已经通过。后续证据可以增强相应恢复场景的结论，便携备份的范围和大小限制保持不变。

## D1 原生 SQL 备份与迁移

导出前记录代码版本、migrations 版本、活动 `sourceId/generation`、revision 和备份时间。下面命令供运维执行；`--remote` 会操作配置所指的真实资源。本次文档工作没有执行远端导出、导入或部署。

```bash
# 使用专用源配置，核对账号和 database_id 后执行。
umask 077
mkdir -p output/recovery
pnpm exec wrangler d1 export DB --remote --config wrangler.source.toml --output output/recovery/mailhub-d1.sql
```

不要只导出可见的业务表：`storage_meta`、`storage_rows`、迁移记录和 ID 序列也关系到恢复。若当前主库在外部数据库，以上导出只保存 D1 的内容；它可能只是历史数据或旧副本。

恢复演练应创建**空的、独立的 D1 数据库**，在单独目标配置中绑定，再导入 SQL：

```bash
# wrangler.recovery.toml 必须绑定新建的恢复测试库。
pnpm exec wrangler d1 execute DB --remote --config wrangler.recovery.toml --file output/recovery/mailhub-d1.sql
pnpm exec wrangler d1 migrations list DB --remote --config wrangler.recovery.toml
# 核对已应用记录和实际表结构后，只应用尚未执行的迁移。
pnpm exec wrangler d1 migrations apply DB --remote --config wrangler.recovery.toml
```

不要先给空库执行全部 migrations 再导入含 `CREATE TABLE` 的全量 SQL，也不要对正在服务的库直接覆盖导入。包含 `ALTER TABLE` 的迁移不能盲目重复执行。当前 `0009_mail_objects.sql` 含 GC 的 `state` 字段；若旧部署已执行过不含该字段的同名迁移，改写文件不会自动升级已执行的数据库，需要新增前向迁移并演练。

SQL 导入成功后，核对表/行数、外键与唯一约束、`storage_meta` revision/counters、数据集内容和凭据解密。D1 中保存多个 generation 时，DO 才知道哪个是当前活动数据集。**只复制 SQL 并新建协调器不会自动选中原活动 generation**：新协调器默认指向 `d1/legacy`。不要通过手改元数据绕过版本或所有者检查；保留原协调器的恢复和丢失协调器的恢复是不同流程。

同一协调器仍可用时，换外部数据库服务器优先按 [数据源文档](DATABASES.md)“添加新数据源 → 同步 → 校验 → 切换”操作。D1 原生 SQL 和平台自身提供的恢复能力只能作为对应数据库的备份层，不会恢复 DO、R2 或 Worker Secrets。

## 外部数据库的生产副本与独立备份

应用存储使用 MySQL 的 `mailhub_meta_v1` / `mailhub_rows_v1`、MongoDB 同名集合，或 Redis 数据集命名空间中的 Hash。备份要把行数据、版本、删除标记、计数器和 owner 信息作为一致整体保存，不能只导出 UI 列表。

| 主库             | 生产备份建议                                                                                                                     | 恢复验证                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| MySQL 8 / InnoDB | 专用库一致性逻辑/物理备份，按恢复点需求保存 binlog；生产复制之外再留独立历史备份                                                 | 在新实例恢复，核对 meta 与 rows、事务、TLS 和 Connector 健康检查                |
| MongoDB 副本集   | 使用支持副本集一致性的快照或备份工具；需要时间点恢复时保留相应 oplog                                                             | 恢复到副本集，检查索引、元数据和多数派事务；standalone 不满足当前适配器要求     |
| Redis 7          | 主库存储要求 `appendonly yes`、`appendfsync always`、`maxmemory-policy noeviction`；按供应商/版本流程备份一致的 AOF/RDB 与持久卷 | 在独立实例验证持久化配置和完整数据集；不能把运行中的多个 AOF 文件任意拼接成备份 |

副本用途的免费 Redis 可能没有可验证的持久化。应用“同步副本”是一次性 snapshot，不提供持续订阅、定时计划或源失效后的自动提升。数据库复制也会传播误删；应有独立保留周期的历史备份，定期验证能从备份恢复。

数据库连接账号、Connector 的 sources 文件/服务令牌、TLS 配置和运行镜像也要备份。协调器保存的 source ID、generation 与 owner 需要与原生备份配套。应用禁止两个独立控制器同时接管同一个已有数据集；克隆数据库后直接用新控制器连接，不等于已经完成接管。没有原协调器状态时，当前没有通用的一键 owner 重绑/数据集接管流程。

源服务器已永久不可读时，“同步并切换”不能补回尚未同步的写入。应先恢复源库或使用已验证的原生备份；不要把强制改活动指针当作灾备方案。

## R2 原始邮件、附件与 GC 保留

配置 `MAIL_OBJECTS` 后，原始 EML 存在 `mail/<uuid>/raw.eml`，附件下载从该 EML 解析。便携备份和数据库备份仅保存 key、附件清单及正文，不包含 EML 字节。没有启用 R2 时的历史邮件不会凭空生成原始文件。

- 上传前先记录待回收标记；未成功提交邮件的孤儿对象，**24 小时**后具备回收资格。
- 删除邮件或清理邮件时，对象进入 GC 队列，**7 天**后具备回收资格。时间从删除/入队计算，不是从备份创建时计算。
- GC 默认由每 15 分钟的定时任务触发，每轮最多取 50 条；失败会延迟重试。因此实际删除可能更晚，不能把延迟当作额外保留承诺。
- 原子认领会检查当前数据集中的活跃引用，置为 `deleting` 后拒绝晚到确认；恢复也检查删除标记和数据版本。这保护应用内并发，不能阻止管理员或外部生命周期规则直接删除 R2 对象。
- GC 不遍历所有历史 generation 或便携文件。旧备份里存在 key 不会阻止当前 GC；旧数据库副本也不会自动延长对象保留。

为每个可恢复备份保留独立对象副本：复制其引用的 EML，保持原 key，记录对象数量、字节数与独立 SHA-256 清单，将副本存放在应用 GC 不会访问的位置。独立副本的保留期应覆盖数据库备份的全部保留期。可以使用受支持的 R2/S3 工具或服务商备份流程，切勿将同步删除选项传播到唯一的历史备份。

恢复时先把独立副本复制到目标私有桶并配置 `MAIL_OBJECTS`，核验 key、字节数和摘要，再做业务预览与恢复。当前 API 使用 R2 `HEAD` 验证存在性，**不校验 EML 内容哈希**；“文件存在”不能证明内容与备份匹配。还应通过下载核对原始 EML、UTF-8 文件名和二进制附件。

若向已有环境的同一桶还原原 key，应先安排维护窗口、暂停 GC 调度并确认在途删除已结束，再复制文件和恢复业务引用。该暂停由运维流程实施，当前没有专用的 R2 恢复锁接口；使用独立恢复桶可以避免与生产 GC 同时操作对象。

超过 7 天后仅有 SQL/JSON 可能仍能恢复正文和元数据，却无法恢复已删除的 EML/附件；当前便携恢复遇到缺失的引用对象会拒绝，并不会自动降级为只有正文。缺少独立对象备份时需要人工评估，不能宣称文件已完整恢复。

## 密钥备份与凭据轮换

至少独立保管以下材料及其版本/使用时间，访问权限与备份文件分开管理：

| 材料                                                  | 用途与恢复依赖                                                        |
| ----------------------------------------------------- | --------------------------------------------------------------------- |
| 便携备份口令                                          | 解密对应便携文件；与 Worker 凭据密钥不是同一概念                      |
| `CREDENTIAL_ENCRYPTION_KEY`                           | 当前业务凭据加密；没设置时使用 `STORAGE_ENCRYPTION_KEY` 回退值        |
| `CREDENTIAL_ENCRYPTION_KEY_PREVIOUS`                  | 轮换窗口内兼容旧业务密文；只支持一个 previous 值                      |
| `STORAGE_ENCRYPTION_KEY`                              | 解密 DO 中保存的 Connector 令牌/Redis URI；也可能是业务凭据的回退密钥 |
| `COOKIE_SECRET`、管理员/会话设置及其他 Worker Secrets | 登录、会话和幂等响应解密等；原环境控制数据恢复需要对应材料            |
| Microsoft/Telegram/Connector 等外部凭据               | 恢复集成；不包含在便携备份中，仍受外部服务权限与有效期限制            |

不要把“Secrets 已上传到 Cloudflare”当作离线备份。保留可离线访问的受控密钥副本，并在隔离环境验证解密；丢失密钥后重新生成同名 Secret 不能解密旧数据。

### 轮换业务凭据密钥

1. 备份当前活动数据集、现有密钥及其版本，确认凭据可读。若业务一直回退使用 `STORAGE_ENCRYPTION_KEY`，本次把它作为旧业务密钥保留，同时设置独立的新 `CREDENTIAL_ENCRYPTION_KEY`；暂不改变连接加密密钥。
2. 先将旧的有效业务密钥配置为 `CREDENTIAL_ENCRYPTION_KEY_PREVIOUS`，再将至少 32 字符的新随机密钥配置为 `CREDENTIAL_ENCRYPTION_KEY`。同一轮尚未处理完时不要再次覆盖 previous。
3. 以管理员会话访问 `POST /api/settings/credentials/rekey`，分别处理 `accounts`、`platform_vault`、`oauth_sessions`、`webhooks`。数字 ID 表从 `cursor: 0` 开始，OAuth 表从 `cursor: ""` 开始。每次按响应 `cursor` 继续，直到 `complete: true`；每批最多 50 行。
4. 检查 `scanned/changed/skipped`。并发凭据更新会使该行跳过，不会被旧值覆盖；有 `skipped` 时再从头扫描，并抽查实际解密。`complete` 只表示游标走完，状态接口的 `plaintext_records: 0` 也不能证明所有密文已经用新密钥重写。
5. 在隔离副本中仅配置新密钥验证四类凭据的解密，核对轮换后新备份可用，再移除生产 previous。旧 generation、旧快照和原生备份没有被本次重加密；只要仍保留这些备份，就要离线保留相应旧密钥。

当前轮换覆盖账号密码/refresh token、台账密码/TOTP、OAuth verifier、Webhook secret/URL，并更新 token 查询用的指纹。它不是对全部数据库字段的统一重新加密，也不会轮换 R2 文件、便携文件口令、会话签名或历史幂等响应。

### 连接加密密钥的边界

`STORAGE_ENCRYPTION_KEY` 的连接密文读取没有 previous 回退，也没有协调器连接配置的批量重加密接口。**不要直接替换它并期待 `/credentials/rekey` 修复连接。** 如需轮换，应先保存全部真实连接配置、数据库原生备份与控制态恢复方案，在隔离环境制定连接重录/迁移计划；当前不提供无中断的一键连接密钥轮换。

## Durable Object 控制态与跨账号恢复

`STORAGE` 的 SQLite Durable Object 通过 `control_chunks` 保存控制状态。实际内容包括 `state` 中的 owner、活动数据集、revision、连接配置密文、迁移任务、旧指针、安全设置镜像、未确认提交 outbox，以及迁移重放日志 `log:*`、恢复回执 `restore:*` 等。alarm 调度也关系到任务继续执行。

`GET /api/settings/storage` 只返回经过脱敏的状态摘要；它不是控制态导出，缺少连接密文、owner、outbox、重放日志和恢复回执。D1 SQL 导出不包含这个独立 DO 的 SQLite 存储。当前源码没有完整控制态导出、验证、导入及跨账号恢复工具；如果依赖平台自身的 DO 恢复能力，必须另行核实可用范围与保留时间，并与数据库版本做配套演练，不能将其视为本项目已交付的接口。

跨 Cloudflare 账号时应区分两个目标：

1. **小规模业务搬迁**：先创建目标 Worker/D1/新协调器，完成 migrations 和独立密钥配置；复制 R2 文件；使用可恢复的加密业务文件预览、恢复和验证。再手工重建 API Key、Webhook、数据源连接、域名、Email Routing、Microsoft 回调地址等目标环境配置，按计划切流。旧会话、旧投递队列、审计、幂等记录和 DO 任务不随文件迁入。
2. **完整灾备/延续旧控制状态**：除原生数据库和文件外，还需要可信的 DO 控制态导出/导入、owner 交接、未确认写入恢复、外部连接和密钥恢复。目前这些没有整合为可执行的一键流程。原协调器丢失、原活动库离线或数据超出便携限制时，应按具体备份和故障状态制定恢复方案，不能保证仅上传一个 JSON 就恢复全站。

Cloudflare 账号、数据库/bucket ID、DO namespace、Worker 绑定、DNS 和域名验证都不能由业务 JSON 自动创建。业务同步也不会迁移别的服务器上的任意数据库，只迁移本应用的数据集。

## 尚未交付的灾备能力

- 完整 DO 控制态的安全导出、导入、版本校验、owner 交接及协调器丢失后的接管流程。
- 数据库、DO 与 R2 的统一一致性备份点、自动备份计划、保留策略和恢复演练调度。
- 备份对 R2 对象的长期保留引用、文件清单摘要校验与跨桶自动恢复。
- `STORAGE_ENCRYPTION_KEY` 所保护连接配置的批量轮换和历史密钥兼容。
- 跨 Cloudflare 账号的一键资源重建、认证/控制记录搬迁，以及大于便携限制的业务文件恢复。

这些缺口应由后续需求单独验收。当前文档和测试证明的是已实现的业务恢复、数据集切换与并发保护，未证明整站跨账号灾备已经完整可用。
